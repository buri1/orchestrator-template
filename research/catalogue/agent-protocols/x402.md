## Overview

x402 resurrects the long-dormant HTTP 402 "Payment Required" status code and turns it into a real payment protocol. Built by Coinbase, it enables instant stablecoin micropayments directly within HTTP request/response cycles — no separate payment rail, no account creation, no API keys. When a server requires payment, it responds with `HTTP 402` including payment instructions; the client pays and retries the request with a payment proof header.

The protocol is chain-agnostic, supporting EVM chains (Ethereum, Base, Polygon) and Solana (SVM), with fiat rails planned. It uses a three-party model: Client (pays), Resource Server (provides the service), and Facilitator (verifies payment and settles). The design is trust-minimizing — facilitators cannot move funds beyond what the client authorizes.

x402 has achieved significant traction: 156,000 weekly transactions, 492% growth, $10M+ volume processed on Solana alone, and integration with Google's Agent Payments Protocol (AP2). Major platforms including Cloudflare, Google, and Vercel support x402. SDKs exist for TypeScript, Python, Go, and Rust.

## Technical Architecture

```
┌──────────┐    1. Request           ┌────────────────┐
│          │───────────────────────►│                │
│  Client  │    2. HTTP 402 +       │  Resource      │
│  (Agent) │◄───payment-required────│  Server        │
│          │    3. Request +        │  (API/Service) │
│          │───payment-proof───────►│                │
│          │    4. Response (200)   │                │
│          │◄──────────────────────│                │
└──────────┘                        └───────┬────────┘
                                            │ verify
                                    ┌───────▼────────┐
                                    │  Facilitator   │
                                    │  (Coinbase/    │
                                    │   Self-hosted) │
                                    │                │
                                    │  Settlement &  │
                                    │  Verification  │
                                    └────────────────┘
```

**Core Abstractions:**

- **Payment Scheme**: Pluggable payment logic (e.g., `exact` for fixed-price, `subscription` for recurring). Each scheme defines how payment proofs are created and verified.
- **Network**: Blockchain implementation (EVM, SVM). Networks handle chain-specific signing and verification.
- **Facilitator**: Middleware that verifies payment proofs and handles settlement. Can be Coinbase's hosted service or self-hosted.
- **Payment Header**: HTTP header containing the payment proof, added to the retry request after receiving a 402.

**Server Integration (one line):**
```javascript
app.use(paymentMiddleware({
  "GET /weather": {
    accepts: [{ scheme: "exact", network: "base", maxAmountRequired: "0.01", resource: "USDC" }],
    description: "Weather data"
  }
}));
```

**Client Integration:**
```javascript
const response = await x402Fetch("https://api.example.com/weather", {
  paymentToken: wallet.signPayment
});
```

**Key Design Decisions:**
- Zero protocol fees (only gas/network fees)
- No account creation required
- Facilitator cannot move funds beyond client authorization
- Stablecoin-first (USDC) to avoid volatility
- HTTP-native — no separate payment API or webhook flow

## Publisher Background

Coinbase, the largest US-based cryptocurrency exchange (publicly traded, NASDAQ: COIN), built x402 as open infrastructure for the agent economy. This is strategic positioning — Coinbase wants to be the payment rails for AI agents, similar to how Stripe became the payment rails for the web. The protocol launched in May 2025 and has rapidly gained adoption. Coinbase operates the default Facilitator but the protocol is designed for self-hosted facilitators. The inclusion in Google's AP2 framework signals serious enterprise backing.

## What's Valuable for Us

1. **Agent economy enablement**: When we reach Phase 4 and start selling agent services (SaaS factory output, lead gen swarm access, orchestrator-as-a-service), x402 is the simplest way to monetize API endpoints. One middleware call to paywall any endpoint.

2. **Micropayment model for agent-to-agent transactions**: In a federated multi-business architecture, different business lines could charge each other for expensive operations (e.g., a coding agent calling a paid code review service). x402 makes this trivial.

3. **TypeScript-first SDK**: The primary SDK is TypeScript, aligning with our stack. Integration would be straightforward.

4. **MCP integration exists**: x402 already has MCP server implementations, meaning agents with MCP access can make payments. This fits our MCP-heavy architecture.

5. **Stablecoin payments = predictable revenue**: Using USDC rather than volatile crypto means we can price services in dollars and receive dollars. This matters for the contracts business.

---

## What's NOT Relevant

- **Crypto/DeFi complexity**: x402 abstracts away most blockchain complexity, but we still need to manage wallets and handle gas fees. This is friction we don't need until we're actually monetizing agent services.
- **Solana/EVM chain specifics**: The blockchain details are implementation noise for us. We'd use Base (Coinbase's L2) or whatever has the lowest fees.
- **Facilitator self-hosting**: Running our own payment verification infrastructure is overkill. Coinbase's hosted facilitator is fine for our volumes.
