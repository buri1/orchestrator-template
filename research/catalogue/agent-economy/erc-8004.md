## Overview

ERC-8004, proposed on August 13, 2025, and deployed to Ethereum mainnet on January 29, 2026, is an Ethereum standard that extends the Agent-to-Agent (A2A) Protocol with a trust layer. It enables agents from different organizations to discover each other, evaluate trustworthiness, and interact — all without pre-existing trust relationships. The standard was co-authored by engineers from MetaMask, Ethereum Foundation, Google, and Coinbase.

The core insight is separating trust into three distinct, composable concerns: **identity** (who is this agent?), **reputation** (has it performed well?), and **validation** (can its work be independently verified?). Each gets its own lightweight on-chain registry. The standard deliberately does NOT define payment mechanisms — it's unopinionated about how agents get paid, focusing solely on trust and discovery.

The ecosystem already has multiple implementations: JS/TS SDKs (ChaosChain SDK, erc-8004-js), Python (erc-8004-py), Go (Praxis SDK), plus TEE integrations from Automata Network and Phala Network. An open-source marketplace (AgentStore) using ERC-8004 identity with x402 payments already exists. Deployed on multiple testnets (Ethereum Sepolia, Base Sepolia, Linea Sepolia, Hedera) and mainnet.

## Technical Architecture

```
ERC-8004 Trust Layer
├── Identity Registry (ERC-721)
│   ├── register(agentURI, metadata[]) → tokenId
│   ├── Agent Registration File (JSON)
│   │   ├── Service endpoints (A2A, MCP, web, ENS, DID)
│   │   ├── x402 payment support declaration
│   │   ├── Supported trust mechanisms
│   │   └── Active status
│   ├── setAgentWallet() — EIP-712/ERC-1271 signed
│   └── Globally unique: {namespace}:{chainId}:{registry}
│
├── Reputation Registry
│   ├── giveFeedback(value, decimals, tags, endpoint, evidenceURI)
│   ├── revokeFeedback() — withdraw previous signal
│   ├── appendResponse() — dispute/clarify
│   ├── getSummary() — aggregate stats (client-side filtering mandatory)
│   └── Off-chain evidence via IPFS (hash committed on-chain)
│
├── Validation Registry
│   ├── validationRequest(validator, agentId, requestURI, requestHash)
│   ├── validationResponse(requestHash, score 0-100, responseURI, tag)
│   ├── Progressive validation via multiple tagged responses
│   └── Validator economics delegated to protocol implementations
│
└── Design Principles
    ├── On-chain: signals + commitments only (gas-efficient)
    ├── Off-chain: full evidence on IPFS (subgraph-indexable)
    ├── Multi-chain: singleton registry per chain, cross-chain agents
    └── Payment-agnostic: trust ≠ payments (can use x402, ETH, etc.)
```

Key interfaces:
- `register()` / `register(string agentURI)` / `register(string agentURI, MetadataEntry[] metadata)` — three registration levels
- `setMetadata()` / `getMetadata()` — arbitrary key-value on-chain metadata
- `giveFeedback()` — int128 scored feedback with optional categorical tags
- `validationRequest()` / `validationResponse()` — third-party work verification with 0-100 scoring

## What's Valuable for Us

1. **Three-registry separation pattern**: The split of Identity / Reputation / Validation into independent registries is architecturally elegant. Even without blockchain, this pattern could inform how we structure agent trust in our federated system — each business line could have its own agent identity registry.

2. **Agent Registration File schema**: The JSON metadata format for agent capabilities, endpoints, and supported protocols is a useful reference for how to describe agents in a standardized way across our business lines.

3. **Validation Registry concept**: Third-party work verification with 0-100 scoring maps well to our E2E testing gate. We could implement a non-blockchain version: when Agent A completes work, Agent B validates it with a score.

4. **x402 payment compatibility**: The standard's deliberate payment-agnosticism while supporting x402 declarations in agent registration files shows mature thinking about separating concerns.

---

## What's NOT Relevant

- **Blockchain dependency**: Our system is terminal-first, Claude-first. Adding Ethereum transactions to every agent interaction would add latency, cost, and complexity with zero benefit for internal orchestration. Blockchain trust makes sense for cross-organizational scenarios; we're intra-organizational.
- **Gas costs and smart contracts**: Even on L2s, deploying registries and submitting feedback costs gas. Our agents run hundreds of interactions per session — paying per-interaction is economically absurd for our use case.
- **Sybil resistance concerns**: We control our own agents. We don't need censorship-resistant identity or anti-Sybil mechanisms. We know our agents because we spawn them.
- **ERC-721 identity tokens**: Minting NFTs for agent identity is massive overkill for internal systems.

## Future Use Cases

- **Phase 4 (Days 90+)**: If we offer agent-as-a-service to external clients, ERC-8004's identity and reputation registries could provide verifiable trust for clients selecting our agents. The Validation Registry pattern could underpin SLA guarantees.
- **Phase 4+ (Agent marketplace)**: If the vision extends to a marketplace where third-party agents compete for tasks, ERC-8004 becomes the natural trust layer. The x402 payment integration would enable per-task billing.
- **Conceptual adoption now**: The three-registry separation pattern is worth adopting conceptually in our orchestrator state management — tracking agent identity, performance history (reputation), and work validation separately.

---

## Key Takeaway

> **ERC-8004 is the most thoughtful agent trust standard we've seen — the three-registry separation of identity, reputation, and validation is architecturally elegant — but it's blockchain-native infrastructure for cross-organizational agent economies, which is Phase 4+ territory for us at earliest.**
