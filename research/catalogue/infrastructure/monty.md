## Overview

Monty is a from-scratch Python interpreter written in Rust, purpose-built for a single use case: safely executing Python code generated by LLMs. Rather than spinning up Docker containers (195ms), WASM runtimes (66ms), or browser-based Pyodide (2800ms), Monty starts executing in under 1 microsecond because it runs embedded in the host process with no CPython dependency.

The design philosophy is "explicit allowlist" security: the interpreter has zero access to filesystem, network, or environment variables by default. All I/O happens through external functions that the developer explicitly provides. When the LLM-generated code calls `fetch(url)`, execution pauses, control returns to the host, the host performs the actual fetch, and execution resumes with the result. This pause/resume pattern is serializable — you can snapshot the entire interpreter state to bytes, store it in a database, and resume in a different process.

Monty deliberately sacrifices language completeness for security and speed. It supports a subset of Python sufficient for agent expressions: functions, loops, conditionals, async/await, type hints, and a handful of stdlib modules (`sys`, `os`, `typing`, `asyncio`, `re`). Classes, match statements, and third-party libraries are not supported (classes are planned). The thesis is that LLMs can express tool-calling orchestration logic within this subset, and anything more complex should be handled by the host environment.

Key technical details:

- **Bytecode VM**: Parse Python → compile to custom bytecode → execute on stack-based VM. No CPython AST or runtime involved.
- **MontyObject type system**: All Python values represented as Rust enums (`MontyObject::Int`, `MontyObject::Str`, etc.), enabling strict memory control.
- **External function bridge**: The `start()` / `resume()` API pauses the VM at external function calls, returning a `FunctionSnapshot` with the function name and arguments. The host executes the real function and calls `resume(return_value=...)`.
- **Serialization**: Both `MontyRun` (parsed code) and `FunctionSnapshot` (paused execution) serialize to bytes via `dump()` / `load()`. Enables cross-process, cross-machine execution transfer.
- **Type checking**: Bundled `ty` (from Astral, makers of Ruff/uv) performs optional pre-execution type validation against developer-provided stubs.
- **Resource limits**: `LimitTracker` monitors memory allocations, stack depth, and wall-clock time. Exceeding limits cancels execution deterministically.
- **Crate structure**: `monty` (core), `monty-python` (PyO3 bindings), `monty-js` (napi-rs bindings), `monty-cli` (standalone binary), `monty-type-checking`, `monty-typeshed`.
- **~4.5MB package size** — orders of magnitude smaller than Docker images or Pyodide runtimes.

## What's Valuable for Us

- **Snapshotting pattern for durable agent execution**: The `dump()` / `load()` serialization of paused interpreter state is the most elegant implementation of durable execution we've seen at the interpreter level. This maps directly to our crash recovery needs — if an agent pauses mid-tool-call, the state can be persisted and resumed after a tmux session restart. Worth studying `crates/monty/src/bytecode/vm/` for the serialization implementation.

- **External function bridge as security primitive**: The "all I/O through explicit host functions" model is a clean implementation of our Master Blueprint's Governing Principle #2 (deterministic orchestration, LLM execution). The orchestrator controls exactly what the agent code can do by controlling which functions are exposed.

- **Resource limit enforcement**: Configurable memory, stack depth, and execution time limits with deterministic cancellation. This is what we'd need if agent-generated code runs in our system — preventing runaway computations without container overhead.

- **Performance comparison table**: Monty's README contains the best side-by-side benchmark of sandbox technologies we've encountered. The startup latency numbers (0.06ms vs 195ms Docker vs 2800ms Pyodide vs 66ms WASI) are valuable reference data for any sandbox decision.

- **Code-mode thesis validation**: Cloudflare, Anthropic, and Hugging Face all converging on "LLM writes code instead of tool calls" is a strong signal. Monty is the first purpose-built runtime for this pattern.

## What's NOT Relevant

- **Our agents don't write Python for execution**: Our L-Thread agents run full development workflows (git, npm, build tools, test suites) via Claude Code. They don't generate sandboxed Python snippets. Monty solves a different execution model than ours.

- **Limited Python subset**: No classes, no third-party libraries, limited stdlib. Our agents need full language capabilities when they write code. Monty is deliberately restrictive in ways that conflict with general-purpose coding agents.

- **Python-centric ecosystem**: Our stack is TypeScript-first (Master Blueprint Layer 3). While Monty has JS bindings, the primary integration path is through PydanticAI — a Python framework we don't use.

- **Single-expression focus**: Monty is designed for agent orchestration expressions (call tools, combine results, return). It's not a general-purpose sandbox for running test suites, build scripts, or development workflows.

## Future Use Cases

- **Phase 2 (Days 4-60)**: No direct use. But the snapshotting pattern is worth studying as a reference for our own state persistence improvements.

- **Phase 3 (Days 60-90)**: If we build SaaS factory products that need user-facing code execution (data analysis tools, workflow builders, chatbots with code execution), Monty becomes a serious candidate. Its MIT license, <1us startup, and 4.5MB size make it ideal for embedding.

- **Phase 4 (Days 90+)**: If the "code mode" paradigm proves superior to traditional tool calling (as Cloudflare, Anthropic, and HuggingFace predict), we may want to adopt PydanticAI's CodeModeToolset pattern. Monty would be the runtime. This is the strongest long-term relevance case.

- **Phase 4 (Days 90+)**: Multi-tenant agent execution in SaaS products. Where E2B/Daytona provide container-level isolation, Monty provides process-embedded isolation at microsecond latency — different tradeoff, potentially complementary.
