# Real-World Orchestration Systems Built on Pi Agent

**Date:** 2026-03-05
**Author:** Systems Research Agent
**Scope:** Comprehensive survey of actual orchestration systems people have built on top of Pi Agent (pi-mono), including architectural patterns, communication methods, state management, scale limits, and failure modes
**Method:** GitHub repository analysis, social media threads, blog posts, documentation review, and cross-referencing with the L-Thread Orchestrator migration feasibility study

---

## Executive Summary

The Pi Agent ecosystem has produced at least **twelve distinct orchestration systems** in the four months since Pi's extension system stabilized (v0.35.0, late 2025). These range from single-file tmux wrappers to enterprise-grade monorepos with 30+ extensions. Every system converges on the same five architectural primitives: (1) filesystem isolation via git worktrees, (2) tmux as the process supervisor, (3) file-based or SQLite-based messaging, (4) hierarchical task decomposition, and (5) eventual consistency through git merge. The systems diverge primarily on **communication topology** (hub-and-spoke vs. peer-to-peer vs. chain) and **observability depth** (silent background vs. full TUI overlay).

This document catalogs what exists, what works, what breaks, and what patterns have emerged as canonical.

## 1. The Ecosystem Map

Pi Agent (pi-mono by Mario Zechner / @badlogicgames) deliberately ships without built-in sub-agent support. As Zechner stated on X: "People of pi all build their own subagent support, while I, a caveman, enjoy two parallel sessions top, without any such fanciness." And later: "and now you know why pi doesn't have subagents built-in."

This design choice has produced a Cambrian explosion of community orchestration approaches. The ecosystem stratifies into three tiers:

| Tier | Category | Examples | Maturity |
|------|----------|----------|----------|
| 1 | Production orchestrators | Overstory, ComposioHQ Agent Orchestrator, Paperclip | High |
| 2 | Pi-native extensions | pi-side-agents, pi-collaborating-agents, pi-subagents, pi-messenger, pi-foreground-chains | Medium |
| 3 | Adjacent/compatible tools | dmux, agtx, multi-agent-workflow-kit, Sidecar | Early |

Additionally, **Oh-My-Pi** (can1357's fork of pi-mono) represents an alternative path where sub-agents, LSP, browser, and MCP are built in rather than bolted on via extensions.

## 2. Tier 1: Production-Grade Orchestrators

### 2.1 Overstory (jayminwest)

**Repository:** [github.com/jayminwest/overstory](https://github.com/jayminwest/overstory)
**Version:** 0.5.6 (as of March 2026)
**Runtime adapters:** Claude Code, Pi Agent

Overstory is the most architecturally complete orchestrator in the Pi ecosystem. It uses instruction overlays and tool-call guards to turn agent sessions into orchestrated workers.

**Architecture:**

- **Agent organization:** Reusable `.md` agent definitions (the HOW) combined with per-task `CLAUDE.md` files generated by `overstory sling` (the WHAT: task ID, file scope, spec path, branch name). The orchestrator works with a Team Lead (can spawn sub-workers) and Specialist Workers (leaf nodes).
- **Isolation:** Each agent runs in an isolated git worktree via tmux.
- **Communication:** Custom SQLite mail system using WAL mode, achieving approximately 1-5ms per query. Supports typed protocol messages and broadcast.
- **Merge strategy:** FIFO merge queue with 4-tier conflict resolution to merge agent branches back to canonical.
- **Monitoring:** Tiered watchdog system -- Tier 0 is a mechanical daemon, Tier 1 provides AI-assisted triage, Tier 2 is a dedicated monitor agent.
- **Runtime-agnostic:** The `AgentRuntime` interface defines the contract. Each adapter handles spawning, config deployment, guard enforcement, readiness detection, and transcript parsing for its runtime.

**What makes it notable:** Overstory is the only system that explicitly warns users about its own limitations: "Agent swarms are not a universal solution. Do not deploy Overstory without understanding the risks -- compounding error rates, cost amplification, debugging complexity, and merge conflicts are the normal case, not edge cases."

### 2.2 ComposioHQ Agent Orchestrator

**Repository:** [github.com/ComposioHQ/agent-orchestrator](https://github.com/ComposioHQ/agent-orchestrator)
**Blog post:** [pkarnal.com - Open-Sourcing Agent Orchestrator: Effectively Manage 30 Parallel Agents](https://pkarnal.com/blog/open-sourcing-agent-orchestrator)

Agent Orchestrator manages fleets of AI coding agents working in parallel. Each agent gets its own git worktree, its own branch, and its own PR. When CI fails, the agent fixes it. When reviewers leave comments, the agent addresses them.

**Architecture:**

- **Scale proven:** 30 concurrent agents across 40 worktrees in production, with a dashboard showing real-time status of each agent.
- **Self-bootstrapping:** The system was built by itself using agents -- 30 concurrent agents working on Agent Orchestrator, managed by the bash-script version of itself while building the TypeScript replacement.
- **CI integration:** Automatic CI failure detection and fix routing. Agents receive CI failure logs, attempt fixes, and re-push.
- **Review integration:** PR review comments are automatically routed to the responsible agent for resolution.

**What makes it notable:** This is the highest-scale Pi-compatible orchestrator documented. The 30-agent threshold represents a practical ceiling where coordination overhead starts to dominate.

### 2.3 mmeyer/pi-agent-example

**Repository:** [github.com/mmeyer/pi-agent-example](https://github.com/mmeyer/pi-agent-example)

An enterprise-grade monorepo containing the agent core, a multi-channel gateway, 40+ skills, 30+ extensions, and 20+ specialized subagents. Extensions cover interactive CLI overlays, multi-agent chains, planning modes, role-based memory, and Q&A interfaces. Skills include semantic code search, web browser automation, terminal control, documentation management, and office suite support.

**What makes it notable:** The sheer breadth demonstrates Pi's extensibility ceiling. This is what a fully "batteries-included" Pi installation looks like when someone builds everything themselves rather than using Oh-My-Pi's built-in features.

## 3. Tier 2: Community Extensions for Pi

These are the building blocks that most Pi-based orchestrators use. They are npm-installable Pi extensions.

### 3.1 pi-side-agents (pasky)

**Repository:** [github.com/pasky/pi-side-agents](https://github.com/pasky/pi-side-agents)
**Pattern:** Hub-and-spoke, tmux-based

The foundational sub-agent extension for Pi. Each child runs in its own tmux window and git worktree. Instead of waiting for one backlog item to finish before starting the next, you spin tasks out into single-use child agents as soon as they occur. Each child is a one-off and lives and dies with its short topic branch and tmux window.

**Tools provided:**

| Tool | Purpose |
|------|---------|
| `agent-start` | Spawn a new agent in tmux window + worktree |
| `agent-check` | Poll agent status and output |
| `agent-wait-any` | Event-driven wait for any agent to complete |
| `agent-send` | Send instructions to a running agent |

**Key design decisions:**
- Old worktrees are kept around and reused; old branches are auto-pruned during reuse by a new agent. This avoids the disk space explosion that Alex Lavaee documented (9.82 GB consumed by automatic worktree creation in a 20-minute session with a ~2 GB codebase).
- Side agents can also be spawned and controlled by another agent, enabling meta-orchestration where the orchestrator itself is a Pi agent managing a flock.
- Supports model override per agent (e.g., `/agent -model gpt-5.3-codex add regression tests for auth`).

### 3.2 pi-collaborating-agents (baochunli)

**Repository:** [github.com/baochunli/pi-collaborating-agents](https://github.com/baochunli/pi-collaborating-agents)
**Pattern:** Peer-to-peer messaging with file reservation

The most feature-rich messaging extension. Provides autonomous agent-to-agent communication without requiring a central orchestrator.

**Communication model:**
- Dedicated `agent_message` tool for agent-to-agent messaging.
- Inbox delivery uses Pi's message routing: normal messages queued with `followUp`, urgent messages interrupt immediately with `steer`.
- Supports direct messages and broadcast.

**File reservation system:**
- Reservations enforced by hooking Pi's `edit` and `write` tools.
- When an agent tries to edit a reserved file, the tool call is blocked and the agent sees who reserved it, why, and a suggestion to coordinate via `agent_message`.
- Write and edit calls are blocked when another active agent has a matching reservation. Reads remain allowed.

**Sub-agent types:** Scout, documenter, reviewer. Parent (orchestrator) sessions automatically collect final subagent outputs on completion without requiring subagents to send a separate final summary.

**State storage:** `~/.pi/agent/collaborating-agents/` with a registry directory for agent JSON files, inbox directories for inbound messages, and a `messages.jsonl` append-only log.

### 3.3 pi-subagents (nicobailon)

**Repository:** [github.com/nicobailon/pi-subagents](https://github.com/nicobailon/pi-subagents)
**Pattern:** Chain orchestration with depth guards

Focuses on structured delegation with chains, parallel execution, and async dispatch.

**Key features:**
- **Chains:** Commands use arrows to separate steps, allowing scout -> planner -> reviewer workflows in sequence.
- **Parallel execution:** Multiple subagents run concurrently with configurable concurrency.
- **Async dispatch:** Async runs write a dedicated observability folder containing `status.json`, `events.jsonl`, and subagent log files.
- **Depth guards:** Nesting limited to 2 levels by default (main -> subagent -> sub-subagent). Deeper calls are blocked and return an error with guidance. This prevents the recursive agent spawning problem that several teams have encountered.
- **Artifacts:** Subagent artifacts stored in `{sessionDir}/subagent-artifacts/` or `<tmpdir>/pi-subagent-artifacts/`.

### 3.4 pi-messenger (nicobailon)

**Repository:** [github.com/nicobailon/pi-messenger](https://github.com/nicobailon/pi-messenger)
**Pattern:** Chat-room style peer-to-peer

Multiple agents in different terminals sharing a folder can talk to each other like they are in a chat room. No daemon, no server -- just files.

**Architecture:**
- Agents can join, see who is online, see what others are doing, claim tasks, reserve files, and send messages.
- Incoming messages wake the receiving agent via `pi.sendMessage()` with `triggerTurn: true` and `deliverAs: "steer"`, which injects the message as a steering prompt that resumes the agent.
- All shared state (registry, inboxes, swarm claims/completions) lives in `~/.pi/agent/messenger/`.
- Activity feed and crew data are project-scoped under `.pi/messenger/` inside the project.
- Crew agents ship with the extension (`crew/agents/*.md`) and are discovered automatically.

**What makes it notable:** This is the closest Pi equivalent to Claude Code's native Teams/SendMessage system, but built entirely on the filesystem with no IPC, no sockets, and no daemon processes.

### 3.5 pi-foreground-chains (nicobailon)

**Repository:** [github.com/nicobailon/pi-foreground-chains](https://github.com/nicobailon/pi-foreground-chains)
**Pattern:** Observable chain orchestration

A skill (not an extension) that chains multiple AI agents with file-based handoff. Each step runs in an observable overlay where the user watches and can intervene.

**Workflow:** Scout -> `context.md` -> Planner -> `plan.md` -> Worker -> `impl.md` -> Reviewer, with `progress.md` tracking complete history. Builds on pi-interactive-shell for the TUI overlay.

**What makes it notable:** This is the only Pi orchestration approach that prioritizes user observability over autonomy. Every other system runs agents in the background or in separate tmux panes. pi-foreground-chains keeps the human in the loop at every step.

## 5. Architectural Patterns That Recur

Alex Lavaee's analysis ("Five Architectural Primitives Every Agent Swarm Rediscovers") documented that two independent teams (Cursor and Anthropic) converged on the same five primitives without coordinating. The Pi ecosystem independently converged on the same set:

### Primitive 1: Hierarchical Task Decomposition

Every successful Pi orchestrator decomposes work into a tree. The orchestrator agent does not write code -- it decomposes, assigns, reviews, and merges. This matches the L-Thread Orchestrator's "DU BIST KEIN ENTWICKLER" rule.

- **Overstory:** Team Lead -> Specialist Workers (leaf nodes)
- **pi-subagents:** Depth-guarded chains with max 2 levels
- **pi-foreground-chains:** Scout -> Planner -> Worker -> Reviewer
- **Composio:** Planner agent decomposes, worker agents execute

Flat structures where all agents have equal status and self-coordinate through a shared filesystem were tried and abandoned. Cursor documented this directly: agents held locks for too long and forgot to release them.

### Primitive 2: Filesystem Isolation via Git Worktrees

Every system uses git worktrees for agent isolation. This is not coincidental -- it is the only mechanism that provides:
- Full filesystem independence (agents cannot clobber each other's in-progress edits)
- Automatic branching (each worktree is on its own branch)
- Merge infrastructure (git merge handles conflict detection and resolution)
- Cost-effective isolation (a worktree shares the `.git` directory, unlike a full clone)

**Known limitation:** LSP does not work in worktrees. Agents in worktrees cannot lint or get type-checking feedback. Alex Lavaee documented this as a significant gap. Oh-My-Pi's built-in LSP support may help here, but worktree + LSP integration remains unsolved.

### Primitive 3: tmux as Process Supervisor

Every system uses tmux to manage agent lifecycles. tmux provides:
- Session persistence across terminal disconnects
- Named sessions/windows for agent identification
- `capture-pane` for reading agent output without IPC
- `send-keys` for injecting instructions without IPC
- Window/pane lifecycle management (create, kill, list)

This is identical to the L-Thread Orchestrator's tmux approach, validating that pattern.

### Primitive 4: Eventual Consistency Through Git Merge

Both Cursor and Anthropic discovered that eventual consistency via git merge is the right consistency model for agent swarms. Cursor described it: "Sometimes multiple agents touch the same file... Instead of trying to stamp these out completely or overengineer a solution, we accept some moments of turbulence and let the system naturally converge."

Pi-collaborating-agents adds file reservation on top of this, which reduces merge conflicts but does not eliminate them. Overstory's 4-tier conflict resolution represents the most sophisticated merge strategy in the ecosystem.

### Primitive 5: Structured Communication Contracts

The GitHub blog documented that "most multi-agent workflow failures come down to missing structure, not model capability." When agents exchange messy language or inconsistent JSON, workflows fail silently.

The Pi ecosystem addresses this with:
- **pi-collaborating-agents:** Typed message protocol with action field (reserve, release, status, direct, broadcast)
- **Overstory:** SQLite-backed typed protocol messages
- **pi-subagents:** Chain definitions with explicit input/output contracts
- **pi-foreground-chains:** File-based handoff with named artifacts (context.md, plan.md, impl.md)

## 6. Communication Methods Compared

| Method | Used By | Latency | Reliability | Complexity |
|--------|---------|---------|-------------|------------|
| **SQLite WAL** | Overstory | 1-5ms per query | High (ACID) | Medium |
| **JSONL files** | pi-collaborating-agents, pi-messenger | 5-20ms (fsync) | Medium (no ACID) | Low |
| **tmux capture-pane** | pi-side-agents, L-Thread | 10-50ms | Low (buffer overflow) | Low |
| **Named files** | pi-foreground-chains | Filesystem-bound | High (durable) | Very low |
| **Pi sendMessage steer** | pi-messenger | Immediate (in-process) | High | Low |

**The dominant pattern is file-based messaging.** No Pi orchestrator uses sockets, HTTP, or any network protocol. This is deliberate -- file-based messaging works within a single machine, survives process crashes (the messages are on disk), and requires no daemon processes.

The one exception is Overstory's SQLite approach, which provides ACID guarantees at the cost of additional complexity. The WAL-mode SQLite approach is worth noting because it solves the "torn read" problem that JSONL files have when a writer crashes mid-line.

## 7. State Management Approaches

### 7.1 Pi-Native State (appendEntry + JSONL)

Pi's `appendEntry()` writes state into the session JSONL file. This survives compaction (the compaction summary includes entry data) and is navigable via `/tree`. However, it is session-scoped -- lost on `/new`.

**Who uses this:** OpenClaw (for session continuity across heartbeats), most Pi extensions for transient state.

### 7.2 External JSON/JSONL Files

Writing state to files in a known location (e.g., `_bmad/*.json`, `~/.pi/agent/*/`). This survives session changes and is readable by external tools.

**Who uses this:** pi-collaborating-agents (`~/.pi/agent/collaborating-agents/`), pi-messenger (`~/.pi/agent/messenger/` + `.pi/messenger/`), L-Thread Orchestrator (`_bmad/*.json`).

### 7.3 SQLite

Overstory uses SQLite for both messaging and state. Provides ACID guarantees, query capability, and WAL mode for concurrent readers.

### 7.4 Hybrid (Pi appendEntry + External Files)

The recommended approach from the L-Thread migration feasibility study: use `appendEntry()` for session-scoped state that benefits from compaction survival and tree navigation, plus external files for cross-session state that external tools need to read.

### 7.5 Compaction-Aware State

OpenClaw pioneered compaction-aware state management through extensions. Rather than relying on Pi's default summarization, OpenClaw replaces it with a multi-stage pipeline that preserves file operation history and tool failure data. The `session_before_compact` hook receives preparation details and can return a custom summary or cancel the operation entirely.

This is critical for orchestrators because compaction can lose task state. If the orchestrator's current task assignment, review cycle count, or agent status is summarized away, the orchestrator loses its place after compaction.

## 8. Scale: What Works Where

### 1-3 Agents: Everything Works

At this scale, all approaches are viable. tmux capture-pane communication is sufficient, file locking is unnecessary, and merge conflicts are rare.

**Best approach:** pi-side-agents or manual tmux sessions. Minimal overhead.

### 4-10 Agents: File Reservation Becomes Necessary

At this scale, agents begin touching the same files. Without file reservation or worktree isolation, edits collide silently. The "17x Error Trap" documented by Towards Data Science begins to manifest: error rates compound multiplicatively, not additively.

**Best approach:** pi-collaborating-agents with file reservation, or Overstory with worktree isolation + FIFO merge queue.

### 10-30 Agents: Orchestration Overhead Dominates

ComposioHQ's Agent Orchestrator operates at this scale and documented the operational reality: a dashboard is required because no human can track 30 agents by watching tmux panes. CI integration becomes mandatory because manual review of 30 PRs is not feasible.

**Best approach:** ComposioHQ Agent Orchestrator or a purpose-built management plane like Paperclip. The orchestrator agent itself starts to hit context limits tracking 30 concurrent tasks.

### 30+ Agents: Management Plane Required

At this scale, the orchestrator is no longer a single agent -- it is an organizational structure. Paperclip (discussed in Section 11) provides the management plane: org charts, budgets, goal alignment, and heartbeat-based execution. Individual coding agents (which could be Pi instances) are managed as workers within a corporate hierarchy of AI agents.

**Known ceiling:** Alex Lavaee runs 5-10 parallel agent sessions daily and reports that "the biggest bottleneck isn't model capability -- it's that nobody's built the orchestration and environment layer end to end to manage them effectively." Even with tooling, disk space consumption is a concern: automatic worktree creation consumed 9.82 GB in a 20-minute session with a ~2 GB codebase.

## 9. Common Failures and Proven Solutions

### Failure 1: Silent Edit Conflicts

**Symptom:** Agents complete their tasks, PRs merge, but the codebase is broken because Agent A changed a function signature that Agent B's code depended on.

**Frequency:** The most common failure mode. GitHub's engineering blog confirms: "Multi-agent workflows often fail in ways that are hard to explain -- the system completes and agents take actions, but something subtle goes wrong."

**Solutions:**
- **pi-collaborating-agents:** File reservation system blocks concurrent edits to the same file.
- **Overstory:** 4-tier conflict resolution on merge.
- **Cursor's approach (documented by Lavaee):** Accept some turbulence and let the system naturally converge. Run CI after each merge to catch breakage.

### Failure 2: Recursive Agent Spawning

**Symptom:** An agent spawns a subagent to handle a subtask. That subagent spawns another. The tree grows until context windows overflow or the system runs out of tmux windows.

**Solutions:**
- **pi-subagents:** Depth guard limits nesting to 2 levels by default. Deeper calls are blocked with an error message.
- **Oh-My-Pi:** Plan mode disables child spawning entirely, restricting the agent to read-only tools.

### Failure 3: Dead Worker Holds the Lock

**Symptom:** An agent crashes or hangs while holding a file reservation or task lock. No other agent can proceed.

**Solutions:**
- **Lease-based locking:** A worker "leases" a job rather than owning it forever. If it stops heartbeating, the lease expires and another worker can reclaim it. Paperclip implements this pattern.
- **pi-side-agents:** Worktree reuse -- old worktrees are kept around and reused by new agents. The old agent's branch is pruned automatically.
- **Overstory:** Tiered watchdog detects unresponsive agents and triggers recovery.

### Failure 4: Context Window Overflow in Orchestrator

**Symptom:** The orchestrator agent tracks so many concurrent tasks, agent statuses, and conversation history that it exceeds its context window and loses track of what it was doing.

**Solutions:**
- **Tiered context injection:** Load only relevant context per task. The L-Thread Orchestrator's T0/T1/T2 system addresses this. Pi's `context` event hook enables programmatic context pruning before the LLM sees messages.
- **Compaction-aware state:** Use `session_before_compact` to preserve critical orchestration state during compaction. OpenClaw's multi-stage compaction pipeline is the reference implementation.
- **External state files:** Store task state in JSON files that the orchestrator reads on demand, rather than keeping everything in the conversation history.

### Failure 5: Cost Amplification

**Symptom:** Running 10 agents for 30 minutes costs 10x what one agent costs, but delivers less than 10x the output. Redundant API calls and overlapping compute tasks erode ROI.

**Solutions:**
- **Model routing:** Use cheaper models for simple tasks. Pi's multi-provider support enables using Haiku for reviews and Opus for architecture decisions. pi-side-agents supports model override per agent.
- **Paperclip budgets:** Monthly budgets per agent with auto-pause at 100% utilization and soft warning at 80%.
- **Task deduplication:** Atomic task checkout prevents double-work. Both Paperclip and Composio implement this.

### Failure 6: Observability Gap

**Symptom:** The orchestrating instance spawns subagents with zero visibility into what they are doing. Problems go undetected until the final output is wrong.

**Solutions:**
- **pi-foreground-chains:** Every step runs in an observable overlay where the user watches in real-time.
- **pi-subagents:** Async runs write observability folders with status.json and events.jsonl.
- **Overstory:** Tiered watchdog with mechanical daemon (Tier 0), AI-assisted triage (Tier 1), and dedicated monitor agent (Tier 2).
- **Composio:** Real-time dashboard showing status of each of 30 concurrent agents.

## 10. The Oh-My-Pi Alternative Path

Oh-My-Pi (can1357) is a batteries-included fork of pi-mono that builds sub-agents, LSP, browser, MCP, and Python support directly into the agent rather than leaving them to extensions.

**Sub-agent architecture in Oh-My-Pi:**
- Subagents run in-process using `createAgentSession(...)`, `SessionManager`, and direct event subscription. No `child_process` spawn path.
- Isolation via optional git worktree with `ensureWorktree(...)`, `applyBaseline(...)`, `captureDeltaPatch(...)`, and `cleanupWorktree(...)`.
- Full output access via `agent://<id>` resources.
- Isolation backends can use git worktrees or fuse-overlay filesystems with patch/branch merge strategies.
- Async background jobs with configurable concurrency (up to 100 jobs).
- Agent Control Center dashboard for fleet management.

**LSP in Oh-My-Pi:**
- 11 LSP operations: diagnostics, definition, type_definition, implementation, references, hover, symbols, rename, code_actions, status, reload.
- Format-on-write, diagnostics on write/edit, workspace diagnostics.
- 40+ language configurations with local binary resolution.
- This solves the "no LSP in worktrees" problem that plagues all pi-mono-based orchestrators.

**Plan Mode:**
- In plan mode, effective subagent tools are replaced with a restricted set (read, grep, find, ls, lsp, fetch, web_search) and child spawning is disabled. This provides a built-in guard against recursive agent spawning.

**Trade-off:** Oh-My-Pi is at v13.9.2 with a fast release pace. This means more features but more breaking changes. Pi-mono is more stable with fewer features, and the extension ecosystem fills the gaps.

**For L-Thread migration:** If you choose Oh-My-Pi, the migration becomes simpler because sub-agents and MCP are built in. The extension code estimate drops from ~2,300 to ~1,200 lines. But you take on a faster-moving dependency.

## 11. Paperclip: The Management Plane Above Pi

**Repository:** [github.com/paperclipai/paperclip](https://github.com/paperclipai/paperclip)
**Website:** [paperclip.ing](https://paperclip.ing/)
**Creator:** dotta (open-sourced February 2026)

Paperclip operates at a different abstraction level than the Pi extensions described above. It is not a coding agent orchestrator -- it is a **management plane for autonomous companies** where the workers happen to be AI agents.

### Architecture

**Execution model:** Agents do not run continuously. They run in **heartbeats** -- short execution windows triggered by a wakeup. If an agent is already running, new wakeups are merged (coalesced) instead of launching duplicate runs. Agents wake on a schedule, check work, and act.

**Runtime agnosticism:** Paperclip is unopinionated about agent runtimes. Agents can be Claude Code sessions, OpenClaw bots, Pi instances, Python scripts, shell commands, or HTTP webhooks -- anything that can receive a heartbeat signal.

**Atomic operations:** Task checkout and budget enforcement are atomic. No double-work and no runaway spend. This solves the task duplication problem that simpler orchestrators struggle with at scale.

**Persistent context:** Agents resume the same task context across heartbeats instead of restarting from scratch. Paperclip stores session IDs for resumable adapters. Next heartbeat reuses the saved session automatically.

**Budget enforcement:** Monthly budgets per agent with auto-pause at 100% utilization. Soft warning at 80%. The board (human operators) can override limits and resume agents.

**Multi-company isolation:** Every entity is company-scoped. One deployment runs unlimited companies with complete data isolation and separate audit trails.

**Goal ancestry:** Tasks carry full goal ancestry so agents consistently see the "why," not just a title. This addresses the context loss problem where agents lose sight of the high-level objective.

### Paperclip's Relationship to Pi

Paperclip does not replace Pi -- it wraps it. A Paperclip deployment might have 10 "agent" slots, each configured with a Pi agent as the runtime. Paperclip handles the organizational layer (who works on what, with what budget, toward what goal), while Pi handles the coding layer (read files, write code, run tests).

This maps to the L-Thread architecture where the Orchestrator is the management plane and the spawned agents are the workers. The difference is that Paperclip provides the management plane as infrastructure rather than as an LLM prompt.

## 12. Lessons for L-Thread Migration

Based on everything surveyed, these are the actionable patterns for migrating L-Thread Orchestrator to Pi:

### Pattern 1: Use pi-side-agents for Conduit Mode

pi-side-agents maps directly to L-Thread's Conduit Mode. The tool mapping is clean:

| L-Thread | pi-side-agents |
|----------|----------------|
| `conduit pane-split` | `agent-start` |
| `conduit terminal-write` | `agent-send` |
| `conduit terminal-read` | `agent-check` |
| `conduit terminal-wait` | `agent-wait-any` |

The worktree reuse pattern in pi-side-agents is better than L-Thread's current approach, which does not provide filesystem isolation between agents.

### Pattern 2: Use pi-collaborating-agents for Teams Mode

The file reservation system in pi-collaborating-agents is something L-Thread does not have. This alone could prevent the class of silent edit conflicts that are the most common multi-agent failure mode.

### Pattern 3: Use Pi's tool_call Hook for Rule Enforcement

Every L-Thread incident (INC-014, INC-015) would have been prevented by a Pi extension hook. The `tool_call` hook fires before every tool execution. The model cannot bypass it regardless of context length, compaction, or prompt injection.

### Pattern 4: Use External JSON + appendEntry for State

The hybrid approach (external JSON files for cross-session state, `appendEntry` for session-scoped state) is the consensus pattern across the ecosystem. No production system relies solely on either mechanism.

### Pattern 5: Implement Depth Guards

pi-subagents' depth guard (max 2 levels) should be adopted. Without it, recursive agent spawning is a realistic failure mode that can exhaust resources.

### Pattern 6: Build Compaction-Aware State

Use `session_before_compact` to preserve orchestration state. Without this, the orchestrator loses its place after compaction. OpenClaw's multi-stage pipeline is the reference implementation.

### Pattern 7: Adopt File-Based Communication

Every successful Pi orchestrator uses file-based communication. No sockets, no HTTP, no daemon processes. The messaging is durable, crash-recoverable, and requires no infrastructure beyond the filesystem.

### Pattern 8: Consider Paperclip for Scale

If L-Thread grows beyond 10 concurrent agents, Paperclip's management plane (heartbeat execution, atomic task checkout, budget enforcement) becomes necessary. The orchestrator agent itself will hit context limits tracking more than 10 concurrent tasks without a dedicated management layer.
